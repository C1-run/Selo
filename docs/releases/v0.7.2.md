# Selo v0.7.2

Patch release, same day as v0.7.1: one more installer failure path, found by
simulating the one v0.7.1 did not cover.

## The defect

v0.7.1 moved release-metadata discovery to fetch-to-file-then-parse, which
fixed the SIGPIPE race. But the failure branch of the fetch was still wrong:

```bash
curl -fsSL -o "$RELEASE_JSON" ".../releases/latest" || RELEASE_JSON=""
VERSION="$(sed -n '...' "$RELEASE_JSON" 2>/dev/null | head -1)"
```

When curl failed — offline, or the anonymous GitHub API rate limit (60
req/hour per IP; shared CI or office egress hits it) — `RELEASE_JSON` was set
to the empty string. `sed` then errored on the empty filename (exit 2 through
`pipefail`), `set -e` aborted the script **with no message at all**, and the
temp file leaked. A rate-limited install looked like a silent crash.

## The fix

- curl failure is a hard, explained death:
  `could not fetch release metadata (offline, or GitHub API rate limit: anonymous limit is 60 req/hour per IP)`
- a malformed body falls through to the existing
  `could not determine latest version` check instead of dying sideways
- the temp workspace is created up front and cleaned by the EXIT trap, so
  every early die leaves nothing behind

Verified against a real 404 (`SELO_REPO=C1-run/does-not-exist-xyz`): clear
message, exit 1, temp-dir count unchanged across the run. Full happy path
re-verified: checksum, keyless cosign verification, `selo version`, LC_UUID.

## Site: the hero card quotes the served receipt exactly

The selo.c1.run hero card still carried the previous receipt's id while the
download link served the regenerated one — `selo verify` passes either way
(it does not compare the card), but a human comparing them sees a mismatch on
the one page that claims "card matches artifact". The card now shows the
served receipt's id (`c1f-1794618953640600000`) and states plainly that the
runner is a **scripted offender, not an LLM agent**.
