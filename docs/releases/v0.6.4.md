# Selo v0.6.4

Patch release. One fix: the shipped example receipt now verifies.

## What changed

`selo verify` on the project's own `samples/receipt-example.json` returned:

```
Hash:       MISMATCH
Signature:  INVALID
Result:     INVALID
```

For a tool whose entire claim is that a third party can check a receipt with
`selo verify --pubkey`, shipping a sample that does not verify is the wrong example
to set.

Two things were wrong with it:

1. It was **stale** — generated on 2026-10-05 from an older build, so its recorded
   hash and signature no longer match its own contents.
2. It was generated **before the v0.6.1 parser fix**, so its signed `test_output`
   still contained the leaked forbidden file:

   ```
   $ README.md
   [error: exec: "README.md": executable file not found in $PATH]
   ```

   That is precisely the `ParseTaskConfig` section-leak bug v0.6.1 fixed — so the
   shipped sample was advertising the defect in a signed field.

`samples/receipt-example.json` is now a freshly generated, real receipt produced by
the v0.6.3 binary against a small demo repo (a Go module with a passing test and a
`README.md` declared forbidden), with `runner.mode: real`:

```
Verdict:    SUCCESS_WITH_RECEIPT
Hash:       OK
Signature:  OK
Anchor:     OK
Key mode:   persistent
Key source: file
Provenance: PINNED
Result:     VALID
```

The agent made one in-contract change (`billing.go`), never touched the forbidden
`README.md`, and the configured test command passed — so `scans_passed` and
`test_integrity_passed` are both true.

## What you get

- A sample receipt that actually verifies end-to-end with
  `selo verify --pubkey <inline-base64-from-receipt> samples/receipt-example.json`.
- No code, schema, config, or CLI changes. Receipts from v0.6.3 verify unchanged.

## Notes and caveats

- **Receipt hashes are canonical, not byte-exact.** The sample is pretty-printed for
  readability and still verifies — reformatting the JSON does not break the hash.
- `Timestamp: ABSENT` and `Transparency: ABSENT` on this sample because the build
  environment has no RFC3161 TSA or Rekor reachability. Both are opt-in flags
  (`--tsa`, `--rekor`) and are unaffected by this release.
- The receipt records the absolute paths of the machine that produced it
  (`worktree_path`, `runner_command`). That is true of any real receipt and is left
  verbatim — editing it would invalidate the signature.

## Upgrade

Same as v0.6.3: `curl -fsSL https://selo.c1.run/install.sh | sh`. The cosign keyless
identity is unchanged (`C1-run/Selo`, because this is `< v0.7.0`).
