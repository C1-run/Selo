# Selo v0.7.0

Minor release with one deliberate behavior change: **configured commands are
now enforced, not just recorded**. Everything else in this release is
consolidation — one parser, one check-set definition, one shell extractor —
and a new way for receipts to reach the people who decide merges.

## ⚠️ The default flip

Since v0.6.5, a configured command that exited non-zero was **recorded** in
the receipt (`tests_ok: false` / `test_exit_codes`) but the verdict still
keyed off the agent's exit code: `--commands "go test ./..."` failing still
produced `SUCCESS_WITH_RECEIPT` unless you opted in with
`--require-tests-pass`. Teams had to know the gate existed to be protected by
it.

In v0.7.0 the gate is **on by default**:

```
$ selo run "Fix the bug" --commands "go build ./..."   # go build fails
final_verdict : FAILED_REQUIRED_COMMANDS
commands_ok   : false
selo run      : exits 1
```

To keep the recording-only behavior:

```bash
selo run "<goal>" --commands "go test ./..." --no-require-commands-pass
# or: forge.require_commands_pass: false in config/selo.yaml
```

### Why rename "tests" → "commands"

`--commands` accepts any command. With the gate defaulting on, a failing
`go build` or `go vet` would have been reported as `FAILED_TESTS` — labeled
wrong in a signed, verifiable receipt, which is precisely the failure mode
Selo exists to prevent. So the rename and the flip ship together:

| before (v0.6.x) | after (v0.7.0) |
|---|---|
| `--require-tests-pass` (opt-in, default off) | `--require-commands-pass` (default on) + `--no-require-commands-pass` |
| `forge.require_tests_pass` | `forge.require_commands_pass` |
| `FAILED_TESTS` | `FAILED_REQUIRED_COMMANDS` (same severity slot — `selo run` still exits 1) |
| receipt `tests_ok` | `commands_ok` |
| receipt `test_exit_codes` | `command_exit_codes` |
| receipt `tests_passed` | `commands_passed` |

Field renames are receipt-schema changes; per the versioning policy this is a
minor bump, not a patch. The signature covers field *values*, not names, so
existing receipts verify unchanged. The opt-in E2E proof from v0.6.5 now
doubles as the opt-out proof (`TestReceiptRecordsCommandsOKFromExitCodes`
asserts the verdict is not overridden when the gate is off), and new tests pin
the default-on path and the config loader (`TestRequiredCommandsGateFailsRun`,
`TestLoadConfigRequireCommandsPassDefault`).

## Receipts now name their check set: `checks_version`

A receipt's `scans_passed` / `safety_hits` are products of a specific set of
checks with specific semantics. Until now that set was implicit — whoever
reads a receipt must guess which version of the checks produced it.
Receipts now carry `checks_version` (`"1"` in this release) in the signed
bytes: bump the version when check semantics change, and a receipt is never
judged by semantics it was not produced under.

## Receipts now reach the merge decision: PR comments

A receipt nobody reads is a log, not evidence. Selo ships a reusable workflow
that closes the loop — verify, render the decision card, post it as a **sticky
PR comment** (updated in place on re-run, no comment pile-up), and append it
to the job summary:

```yaml
jobs:
  selo-receipt:
    permissions: { contents: read, pull-requests: write }
    uses: C1-run/Selo/.github/workflows/receipt-comment.yml@main
    with:
      receipt-path: runs/run-abc123/receipt.json
      # pubkey: <fingerprint>      # pin the signer in the card
      # fail-on-invalid: true      # fail the job when verify fails
```

Selo's own pull requests run the same arc end-to-end with a mock-mode task
(`.github/workflows/receipt-dogfood.yml`): every PR carries its own receipt
card, signed with `--dev` (CI holds no long-lived key, and the card says so).

## One parser, one check set

Three consolidations, each closing a drift class that already bit once
(BUG-2026-10-13: task-file sections leaked into each other because two
parsers disagreed):

- **One Go parser.** `internal/taskmeta` owns task.md parsing (with fuzz
  tests); `receipt.ParseTaskMeta` and `governor.ParseTaskConfig` delegate to
  it. The daemon also parses each task file **once** now, not twice.
- **One writer.** `taskmeta.Write` is the canonical task.md writer; the old
  hand-rolled writers could silently emit files that parse differently than
  they were built (quoted values were never matchable). `Write` refuses
  values the format cannot represent instead of writing a lie. Round-trip
  test: everything `Write` emits parses back to the same config.
- **One shell extractor.** `fixture_agent.sh` and `c1-loop.sh` extract task
  fields through a shared `scripts/task-parse.sh`, drift-tested against the
  Go parser via subprocess on writer-generated files. Consolidating surfaced a
  real bug: the shell pattern required column-0 list items while every writer
  emits indented ones, so the shell runners' command-execution loops had never
  actually run a command on canonical output.

Relatedly, the daemon's check block (forbidden files, forbidden claims,
secret scan, patch/round limits) now runs through `internal/pipeline.RunAll`.
That package had been dead scaffolding — documented, never called, with
whole-worktree scans that would have regressed the daemon if wired naively.
It is now the single definition of the post-diff check set (diff-scoped),
whose semantics `checks_version` names. The supply-chain BOM and
test-integrity gate run in the daemon flow because they need their full
result objects, but they are part of the same versioned set.

## Docs reconciled with the code

- `internal/pipeline` documented with its real API (the old docs described a
  `Pipeline`/`PipelineContext` API that exists nowhere).
- The containment section no longer lists `docker`/`local` strategies — they
  are refused, and the docs now say so plainly.
- README's "What works" table moved to v0.7 and the receipt docs show the
  renamed fields.
- README states the run-signed vs receiver-signed distinction explicitly,
  citing [arXiv 2606.04193](https://arxiv.org/abs/2606.04193): under the
  default setup the honest ceiling is operator-signed, tamper-evident
  evidence. The structural answer — an independent receiver (CI) co-signing
  the receipt — is designed for, not built yet.

## Upgrade notes

1. If your config sets `require_tests_pass`, rename it to
   `require_commands_pass`. Selo warns on unknown config keys.
2. If any CI reads `tests_ok` / `test_exit_codes` / `tests_passed` from
   receipts, read `commands_ok` / `command_exit_codes` / `commands_passed`.
3. If you relied on non-zero command exits NOT failing the run, pass
   `--no-require-commands-pass` (CLI) or `require_commands_pass: false`
   (config). Nothing else changes: the receipt records the same facts.
