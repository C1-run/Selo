# Selo v0.6.6

Documentation-and-example release. **No code behaviour changes** — Selo's default
is unchanged.

## What changed

v0.6.5 added `--require-tests-pass` but shipped it off by default and left the
guidance thin. This release makes the recommendation explicit where it matters:

- **README "Use in CI"** now shows the flag in context:

  ```bash
  ./selo run "Add feature X" \
    --commands "go test ./..." \
    --require-tests-pass
  ```

  with an explicit warning that it changes what `SUCCESS_WITH_RECEIPT` means.
- **`config/selo.example.yaml`** sets `require_tests_pass: true`, commented as the
  CI-appropriate choice and marked as *not* Selo's default.

## Why the default is still off

This is the part worth reading before you enable it.

| | gate **off** (default) | gate **on** |
|---|---|---|
| `SUCCESS_WITH_RECEIPT` means | the agent's run was not rejected | *and* every configured command exited 0 |
| red test suite | still `SUCCESS`, receipt records `tests_ok: false` | verdict becomes `FAILED_TESTS`; `selo run` exits 1 |
| `scans_passed: true` | safety scans only — says nothing about tests | unchanged |

Both are honest; they answer different questions. The reason Selo does not flip
this by default is that flipping it would **silently rewrite what every
already-issued `SUCCESS_WITH_RECEIPT` asserts** — a receipt that meant "not
rejected" would retroactively read as "tests passed". That is the opposite of what
a signed record is for. Choosing it is a deliberate act, and it should be written
down in your runbook.

CI is the case where the stricter reading is almost always the one you want: a red
suite should block the merge. Hence the example config enables it, and the README
says so in the CI section specifically.

## Compatibility

- No code changes. `require_tests_pass` remains `false` unless you set it.
- `config/selo.example.yaml` is an example, not a shipped default — nothing reads
  it implicitly. Copying it does enable the gate; the comment says so.

## Upgrade

Same as v0.6.5: `curl -fsSL https://selo.c1.run/install.sh | sh`. The cosign
keyless identity is unchanged (`C1-run/Selo`, because this is `< v0.7.0`).
