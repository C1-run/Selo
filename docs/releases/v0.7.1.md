# Selo v0.7.1

Patch release, one day after v0.7.0: a fix for the installer that the
clean-machine install test caught on the release day, plus the receipt
semantics labeling that v0.7.0's default flip called for.

## The installer defect

`install.sh` could not determine the latest release on roughly every other
run, dying with:

```
Error: could not determine latest version
```

while the same command moments later worked. The root cause is a race between
`set -o pipefail` and an early-exiting consumer:

```bash
VERSION="$(curl -fsSL ".../releases/latest" \
    | grep -m1 '"tag_name"' \
    | sed -n 's/.*"tag_name": *"\([^"]*\)".*/\1/p')" || VERSION=""
```

`grep -m1` exits after its first match and closes the pipe. `curl` is still
writing the response body, receives SIGPIPE, and exits 141. Under pipefail
that nonzero status becomes the exit status of the assignment — so the
`|| VERSION=""` fallback ran **even though the version had already been
extracted into the variable**, and overwrote it with empty. The script's own
comment shows the SIGPIPE risk was known: `grep -m1` was picked over `head -1`
to avoid exactly this — but `-m1` has the same early-exit behavior.

Measured on the exact pipeline, same machine, same network: **5 of 8 runs
extracted nothing**; 3 extracted `v0.7.0`.

### The fix

The release JSON is now fetched to a file and parsed from the file — no
early-exiting consumer, nothing to race:

```bash
RELEASE_JSON="$(mktemp)"
curl -fsSL -o "$RELEASE_JSON" "https://api.github.com/repos/$REPO/releases/latest" || RELEASE_JSON=""
VERSION="$(sed -n 's/.*"tag_name": *"\([^"]*\)".*/\1/p' "$RELEASE_JSON" 2>/dev/null | head -1)"
```

Verified stable 3/3 on the parse alone and through a full install (checksum +
keyless cosign verification + `selo version v0.7.0` + LC_UUID present) in a
fresh-HOME sandbox.

## Receipt semantics labeling

v0.7.0 flipped the required-commands gate default, which changes what
`SUCCESS_WITH_RECEIPT` means. A receipt signed before v0.7.0 carries no
`checks_version` — and without a marker, a reader would apply 0.7.0 semantics
to a 0.6.x receipt whose configured commands were recorded but never enforced.

`selo verify` and `selo receipt show` (text and markdown/github cards) now
state it explicitly:

- receipt **with** `checks_version` → `Checks: checks_version 1 — required-commands gate semantics (0.7.0+)`
- receipt **without** → `Checks: pre-0.7.0 — no checks_version; configured commands were recorded but NOT enforced (the gate default flipped in 0.7.0)`

This is a label, not a validity change: old receipts verify exactly as before,
and `selo verify --pubkey <fingerprint>` pins work unchanged.

## Verification

`go build ./...`, `go vet ./...`, full cmd/selo daemon E2E suite, and the
scripts tests green on the release commit. The installer was exercised on a
clean macOS sandbox end-to-end: anonymous download, checksum, keyless cosign
verification, `selo version v0.7.0`, and the Mach-O `LC_UUID` load-command
check that the v0.6.0 post-mortem added as a release gate.
