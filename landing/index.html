From zero to a signed receipt

Works with any agent that can run a shell command. OpenCode and ZCode adapters ship in-repo. macOS and Linux binaries today; Windows builds from source.

curl -fsSL https://raw.githubusercontent.com/C1-run/selo/main/install.sh | bash 
# make signatures attributable across runs
selo keys generate

# initialize a workspace and run a task through the pipeline
selo init
selo run "fix the login bug"

# read the verdict — always from the receipt, never from the agent
selo receipt list
selo receipt show <id> --format github

The install script verifies its checksum and cosign signature, and fails closed. Prefer Go? go install github.com/C1-run/selo/cmd/selo@latest

The verdict, in the pull request

Post the receipt card into a GitHub Actions job summary. No token, no marketplace. The card always shows the integrity state, so a tampered receipt can never look clean.

Running an MCP client? selo mcp serve exposes the real checks, so audit diffs and scan paths without a reimplementation.

No claims without code behind them

Five things the CLI does today. Everything else is in the full table, including what does not exist.

Post-run audit

Forbidden file edits, claims, secrets, patch/round limits, test integrity. Violations reject the task with a signed receipt. Since v0.7, a failing required command fails the run by default.

Signed receipts

Ed25519 over canonical JSON. selo keys generate makes signatures attributable across runs.

One-line third-party verify

selo verify re-checks the receipt's hash and signature. Your client's reviewer does not need your CI.

Worktree containment

The task runs in its own Git worktree. docker/local are refused, not silently degraded.

Exportable evidence

selo receipt export re-signs a receipt as a DSSE-wrapped in-toto Statement v1, verifiable with cosign or slsa-verifier with no Selo install. Optional --tsa and --rekor add an RFC3161 timestamp and a Sigstore transparency log.

What Selo does not do

Read this before you buy anything on this page. The full list lives in the README's Why not Selo counterpoints.

  • Not real-time interception. The audit runs after the agent finishes. A violating change is caught before it reaches your client, but it did happen in the worktree.
  • Not a sandbox. Containment is a Git worktree and policy checks, not process isolation.
  • Not SAST. Heuristic checks govern agent behavior. They will not find SQL injection in your codebase.

Questions buyers actually ask

Is the pilot a hosted service?

No. Selo runs in your workflow. Your agent and repository remain under your control; there is no hosted scheduler or upload service in this pilot.

Does Selo prevent every unsafe change?

No. Its audit runs after the agent finishes. It can flag and reject a run under configured checks, but it is not a complete sandbox or security certification.

How does early access work?

We confirm the repository, acceptance checks, data handling, and delivery terms in writing before kickoff. The first cohort is free in exchange for documented feedback and a publishable case study; paid terms, if any, come only after early access ends. If the agreed pilot cannot be delivered with the existing CLI, it does not happen.

How is this different from secret scanning or CI checks?

Those check specific failure classes inside your pipeline. Selo binds a policy audit to a specific agent run and signs the outcome, so a reviewer outside your CI can re-verify the evidence later.

Can a receipt prove the code is safe?

No. A receipt proves what was checked and what the audit found, signed at a point in time. It is evidence for a human reviewer, not a security certification.

Which agents does it work with?

Any agent that can run a shell command. OpenCode and ZCode adapters ship in the repository, and selo mcp serve exposes the checks over MCP.
